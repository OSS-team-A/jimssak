# 짐싹 최종 UI 프론트 흐름

디자인 기준: Figma `[최종] 짐싹 ui - 11/24수정` 섹션 (`531:8299`). 아래 노드는 모두 이 섹션의 자식이다. 다른 섹션의 예시는 구현 기준으로 쓰지 않는다.

| 연결된 흐름 | 화면·상태 | 현재 API |
| --- | --- | --- |

## 흐름과 데이터 규칙

- 홈의 `촬영하고 이삿짐 정리하기`는 로그인 없이 SC-03으로 간다. 영상 업로드 후에는 SC-06 이사 정보 입력을 거쳐 분석 상태를 확인한다. SC 번호 순서로 이동을 추측하지 않는다.
- SC-13의 네 카드는 **같은 기록의 서로 다른 상태 예시**다. 목록에서는 기록마다 현재 상태의 카드 하나만 표시한다.
- 회원 기록은 계정 소유 이사이며 비회원 기록은 `move_id`와 `X-Guest-Token`으로 접근한다. 현재 백엔드에는 비회원 이사를 회원 계정으로 이전하는 API가 없다. 로그인만으로 비회원 기록이 계정에 연결된다고 안내하면 안 된다.
- `GET /moves/{id}`의 `analysis.status`는 현재 `not_started`, `inventory.status`는 `empty`다. 업로드 성공은 분석 성공이 아니다. 목록·견적·비교에 가짜 결과를 생성하지 않는다.
- 현재 백엔드에는 계정별 이사 기록 목록 API가 없다. 프론트에서 확인 가능한 회원 기록은 이 브라우저 세션에서 만든 이사뿐이다.

## 백엔드 계약 요청

1. 분석 작업 생성/재시도와 작업 상태 조회: `move_id`, 영상 `media_id`, 작업 ID, `queued/running/completed/failed`, 실패 사유, 갱신 시간. 완료 응답에는 물품별 안정적인 ID, 종류·수량·치수·무게 추정·분리 여부·위치·근거 영상 범위를 포함한다.
2. 목록 조회/수정: 물품 추가·수량/치수/특이사항 수정·이사 제외/복구를 개별 ID로 저장하고, 동시 수정 충돌을 구별할 수 있게 버전 또는 갱신 시각을 반환한다. 자연어 채팅 수정은 별도 해석 API와 적용 전 확인 결과가 필요하다.
3. 예상 비용은 확정 목록이 있는 이사에 `POST /api/v1/moves/{move_id}/estimate`로 요청한다. 기본 비교에는 본문이 필요 없다. 회원은 Bearer 토큰, 비회원은 `X-Guest-Token`을 보낸다. 응답의 `ajd`와 `yes2404`에는 각각 `general`, `semi_pack`, `full_pack`의 원 단위 금액이 있다. 화면은 ‘데모 예상가’와 `assumptions`의 가정을 표시한다. 목록의 유효 치수와 수량으로 부피를 합산해 10㎥마다 1톤 차량을 배정한다. 추가 차량은 대당 20만 원이다. 목록 미확정, 당일 인도가 아닌 조건, 1톤 6대 초과는 `409`다. 작업 옵션과 응답 예시는 Swagger에서 확인한다.
4. 이사 후 업로드와 전후 비교: 별도 영상 ID·작업 상태·물품별 `unchanged/suspected/not_visible`과 증거 구간을 반환한다. 직접 확인·미확인·재촬영 결과를 저장할 API가 필요하다.
5. 계정별 이사 목록/상세, 비회원 이사를 로그인 계정에 연결하는 명시적 API가 필요한지 결정한다. 연결 전에는 이관을 약속하지 않는다.

## 검증 범위

각 흐름 PR에서 320px, 390×844, 큰 모바일 폭의 하단 버튼·가로 넘침, 키보드 입력, 브라우저 뒤로가기·새로고침, 오류·빈 상태를 확인한다. 화면별 Figma 스크린샷과 실제 렌더링의 텍스트·간격·색·이미지 비율을 대조하고 `npm run check`, `npm run build` 결과를 적는다. 브라우저 또는 실기기에서 확인하지 못한 항목은 검증 완료로 표시하지 않는다.
