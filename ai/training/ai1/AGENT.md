# pilab-gpuserver용 코드 작성 지침

## 0. 대전제: 완성된 서버 환경에 맞춰 코드를 작성한다

이 프로젝트의 최종 실행 대상은 연구실 공용 GPU 서버 `pilab-gpuserver`이다. 서버의 계정, SSH, GPU 드라이버, 사용자별 Rootless Docker, 저장 공간과 운영 도구는 관리자가 이미 설정했다. 연구원은 각자 자신의 계정으로 접속하고, 자신의 컨테이너 안에서 전달받은 코드를 실행한다.

**에이전트의 목표는 다른 연구원이 프로젝트를 자신의 `/workspace`에 받아서, 문서에 적힌 패키지를 설치하고 명령을 실행하면 같은 기능을 사용할 수 있도록 코드를 완성하는 것이다. 서버를 코드에 맞춰 재설정하는 것을 기본 해결책으로 삼지 않는다.**

이 문서는 서버 밖에서 코드를 작성하는 에이전트에게도 적용된다. Windows 개발 PC에서 동작했다는 사실만으로 서버 호환성이 검증된 것은 아니다. 코드를 전달하는 일과 서버에 접속해 실제 실행하는 일은 구분한다.

## 1. 대상 실행 환경

아래는 2026-11-24 서버 설정 기록에 따른 기준이다. 실제 서버 상태를 확인할 수 있으면 함께 확인하고, 차이가 있을 때 임의로 서버를 변경하지 말고 차이를 보고한다.

| 항목 | 기준 |
| --- | --- |
| 서버 OS | Ubuntu 24.04 계열, Linux x86_64 |
| 실행 방식 | 연구원별 Rootless Docker 컨테이너 |
| 기본 이미지 | `pytorch/pytorch:2.9.1-cuda12.8-cudnn9-devel` |
| 기본 GPU 소프트웨어 | PyTorch 2.9.1 + CUDA 12.8 계열 |
| GPU | NVIDIA RTX PRO 4500 Blackwell 32GB × 2, `sm_120` |
| 시스템 RAM 한도 | 사용자당 112GiB, 컨테이너와 해당 계정의 다른 프로세스 합계 |
| 디스크 쿼터 | 사용자당 경고 450GiB / 최대 500GiB, 이미지·캐시도 사용량에 포함 |
| 개인 영속 저장소 | 컨테이너 `/workspace` = 해당 계정의 서버 `~/workspace` |
| 공용 데이터·모델 | `/data/shared/datasets`, `/data/shared/models`; 컨테이너에서는 읽기 전용 |
| Hugging Face 캐시 | 기본 `HF_HOME=/workspace/.cache/huggingface` |
| 기본 운영 방식 | 한 번에 한 사람 단독 사용, 시작 전에 `lab-status` 확인 |

GPU 드라이버는 호스트가 제공하고 CUDA 사용자 공간 라이브러리는 컨테이너 이미지가 제공한다. `nvidia-smi`에 표시되는 CUDA 지원 버전을 컨테이너의 실제 CUDA 런타임 버전으로 해석하지 않는다. 정확한 Python 버전은 이미지 내부에서 확인하며 추측해서 고정하지 않는다.

## 2. 코드 구조와 실행 인터페이스

- 기존 프로젝트의 구조와 실행 방식을 먼저 확인하고, 필요한 범위에서 서버 호환성을 맞춘다. 단순한 스크립트에 불필요한 프레임워크를 추가하지 않는다.
- 학습·분석·추론에는 터미널에서 실행 가능한 진입점을 제공한다. 노트북이 있더라도 오래 걸리는 본 작업을 실행하는 데 GUI나 셀 수동 실행만 필요하도록 만들지 않는다.
- 진입점에는 `if __name__ == "__main__":` 보호문을 둔다. 모듈을 import하는 것만으로 학습·대규모 다운로드·GPU 할당이 시작되지 않게 한다.
- 데이터 경로, 결과 경로, 배치 크기, 학습 횟수, 장치, seed 등 실제 실행에 필요한 설정은 CLI 인자 또는 명시적인 설정 파일로 받는다. CLI를 도입한다면 `--help`가 실행 방법을 설명해야 한다.
- 백그라운드 실행 중 `input()`, GUI 창, 사용자 클릭을 기다리지 않는다. 필요한 값이 빠지면 원인과 전달 방법을 출력하고 실패 종료한다.
- 학습 과정에서 예외를 숨기거나 실패를 성공 종료로 바꾸지 않는다.

권장 구조는 다음과 같다. 파일명은 기존 프로젝트에 맞춰도 된다.

```text
myproject/
├── AGENTS.md
├── AGENT.md
├── README.md
├── requirements.txt       # 또는 pyproject.toml과 프로젝트에 맞는 의존성 파일
├── train.py               # 작업 종류에 따라 analyze.py, predict.py 등
├── src/
├── configs/               # 설정이 필요한 경우
└── runs/                  # 실행별 결과; Git 추적에서 제외
```

## 3. 경로·데이터·파일 소유권

- 사용자 이름, Windows 드라이브, 개발 PC의 절대 경로, 특정 계정의 `/home/<이름>` 경로를 코드에 하드코딩하지 않는다. 서버 IP와 SSH 계정도 연구 알고리즘 코드에 넣지 않는다.
- `pathlib.Path` 등으로 경로를 처리한다. 상대 경로를 프로젝트 루트와 현재 작업 디렉터리 중 어디에 대해 해석하는지 정하고 README에 명시한다.
- 결과·체크포인트·대용량 캐시는 `/workspace` 아래에 저장한다. 임시 파일은 `/tmp`를 사용할 수 있지만, 보존해야 하는 결과를 그곳에만 남기지 않는다.
- 공용 데이터는 `/data/shared`에서 읽고, 전처리 산출물·분할 정보·수정한 데이터는 개인 `/workspace`에 저장한다. 읽기 전용 공용 경로에 캐시나 인덱스를 쓰는 라이브러리는 쓰기 경로를 별도로 지정한다.
- 사용자가 제공한 경로와 데이터 형식은 실제로 검사하고, 누락 파일과 형식 오류를 구체적으로 알려준다. 실제 데이터가 없으면 임의 데이터로 수행한 검증임을 밝힌다.
- 다른 사람의 홈 디렉터리·컨테이너를 직접 읽는 것을 실행 전제로 삼지 않는다. 코드 공유는 각자의 프로젝트 사본으로, 큰 데이터 공유는 지정된 공용 폴더로 한다.
- 컨테이너 안에 별도 사용자를 만들거나 `docker -u`로 실행하도록 요구하지 않는다. 기존 Rootless Docker의 파일 소유권 매핑을 따른다.
- 기존 실행 결과를 묵시적으로 덮어쓰지 않는다. 실행별 출력 디렉터리나 명시적인 덮어쓰기 옵션을 제공한다.

## 4. 패키지·CUDA 호환성

- 기본 이미지에 설치된 PyTorch와 CUDA를 우선 사용한다. 설치 스크립트에 무조건적인 `pip install --upgrade torch`를 넣지 않는다.
- `requirements.txt` 등에는 필요한 직접 의존성과 검증한 버전 또는 호환 범위를 기록한다. 다른 패키지가 PyTorch·torchvision·torchaudio를 호환되지 않는 조합으로 바꾸지 않는지 확인한다.
- 기본 이미지를 전제로 PyTorch를 의존성 파일에서 제외했다면 그 이유와 이미지 태그를 README에 적는다. PyTorch를 명시한다면 해당 이미지와 맞는 배포 조합을 사용한다.
- `pip freeze`는 실행 환경 기록으로 별도 보관할 수 있지만, 그 결과를 검토 없이 범용 설치 파일로 취급하지 않는다. 로컬 경로·개발 PC 전용 패키지가 섞이지 않도록 한다.
- Blackwell 지원 여부는 버전 숫자만으로 단정하지 않는다. 기본 이미지 조합을 기준으로 하되, 추가 CUDA 확장·FlashAttention·xformers·bitsandbytes 등의 `sm_120`, PyTorch, CUDA 호환성을 별도로 확인한다. 특정 패키지는 프로젝트에서 필요할 때만 추가한다.
- 사전 빌드 wheel이 없는 CUDA 확장은 빌드 도구·지원 아키텍처·설치 절차를 기록한다. 검증하지 않은 확장을 필수로 만들어 실행을 막지 않는다.
- Linux 서버에 Windows 전용 패키지·PowerShell 스크립트가 필수 의존성이 되지 않게 한다. 셸 스크립트는 Linux용 줄바꿈을 사용한다.
- 설치 명령은 환경 창에서 `python -m pip ...`로 실행하도록 작성한다. Python 패키지 때문에 호스트의 드라이버·CUDA·OS를 교체하는 방식으로 해결하지 않는다.
- OS 패키지가 정말 필요하면 컨테이너 내부 의존성으로 구분해 문서화한다. 연구원에게 호스트에서 `sudo apt ...`를 실행하도록 요구하지 않는다.

## 5. GPU·CPU·메모리 사용

- 기본 구현은 보이는 GPU 한 장으로 실행 가능하게 한다. GPU 두 장이 항상 연결된다고 가정하지 않는다.
- 물리 GPU 번호와 컨테이너 안의 논리 GPU 번호를 구분한다. 코드의 `cuda:0`은 컨테이너에서 보이는 첫 번째 GPU이다. GPU 선택은 우선 `lab-env create <환경명> 0` 또는 `1`로 제한하고, 필요하면 환경 내부에서 보이는 장치 번호를 확인한다.
- 모델과 입력 텐서를 같은 장치로 옮긴다. GPU가 필요한 작업에서 GPU가 없으면 명확히 실패하고, CPU 대체를 지원하는 작업이면 장치 선택과 대체 동작을 문서화한다. CPU로 전환한 사실을 숨기지 않는다.
- GPU 두 장을 연결했다고 코드가 자동으로 두 장을 사용하는 것은 아니다. 다중 GPU가 필요한 경우 DDP 등의 초기화·실행 명령·프로세스별 장치 배정을 별도로 구현한다.
- GPU 메모리는 장당 32GB이다. 두 장의 메모리가 자동으로 하나의 64GB 공간이 된다고 가정하지 않는다.
- 배치 크기와 DataLoader worker 수는 조절 가능하게 한다. 전체 데이터를 무조건 GPU나 RAM에 올리지 않는다. 크기가 큰 데이터는 배치 로딩 등을 사용한다.
- CPU·worker·다운로드 병렬도를 무조건 최대로 잡지 않는다. 기본값은 보수적으로 정하고 조절 방법을 제공한다.
- GPU 검증은 장치 목록 확인에 그치지 않고 작은 실제 텐서 연산이나 모델 실행으로 확인한다. 확인 중 GPU가 없을 때 잘못된 장치 인덱스를 조회하지 않는다.

## 6. 장시간 실행·로그·체크포인트

- 긴 작업은 서버 창의 `lab-env run`으로 시작할 수 있어야 한다. 터미널 연결 유지·VS Code 창 유지에 의존하지 않는다.
- 진행도, 주요 지표, 실행 장치, 실제 출력 경로를 로그에 남긴다. `python -u` 또는 적절한 flush·logging 설정으로 로그가 오래 버퍼링되지 않게 한다.
- 긴 학습에는 주기적인 체크포인트와 명시적인 재개 옵션을 구현한다. 모델, optimizer, 완료 epoch 또는 step을 저장하고, 사용하는 경우 scheduler·AMP scaler·난수 상태·데이터 진행 상태도 저장한다.
- 재개 시 설정과 모델 구조가 맞는지 확인한다. `--epochs`가 전체 목표 횟수인지 추가 실행 횟수인지 분명히 정한다.
- 가능하면 같은 파일시스템의 임시 파일에 저장한 뒤 교체해, 저장 중 중단으로 직전 정상 체크포인트가 손상되는 일을 줄인다. 필요 디스크 공간과 체크포인트 보관 개수도 고려한다.
- 정확히 동일한 수치로 재현된다고 검증하지 않았다면 보장하지 않는다. seed·설정·코드 버전·주요 라이브러리 버전을 기록한다.
- **컨테이너 자동 재시작은 학습 자동 재개가 아니다.** 현재 환경의 기본 프로세스는 `sleep infinity`이다. 별도로 실행한 학습 프로세스는 재부팅 후 자동으로 이어지지 않으므로 체크포인트 재개 명령을 제공한다.
- 디스크 쿼터에는 이미지·모델 캐시도 포함된다. 체크포인트를 무한히 쌓거나 데이터를 실행할 때마다 복제하지 않는다.

## 7. README에 반드시 제공할 실행 절차

프로젝트의 실제 파일명과 옵션에 맞춘 명령을 제공한다. 아래의 `myproject`, `research`, `train.py`, 옵션은 설명용이며 구현되지 않은 명령을 그대로 정답처럼 전달하지 않는다.

### 서버 창: 환경과 실행 관리

프롬프트 예: `<계정>@pilab-gpuserver:~$`

```bash
lab-status
lab-env list
```

새 환경이 필요한 경우에만 다음처럼 생성한다. 이미 환경이 있으면 이름과 상태를 확인해 재사용한다.

```bash
lab-env create research 0
```

### 환경 창: 코드 설치와 짧은 검증

VS Code에서 해당 컨테이너에 연결하거나 서버 창에서 `lab-env enter research`로 들어간다. 작업 폴더는 `/workspace/myproject`이다.

프롬프트 예: `root@<환경>:/workspace#`

```bash
cd /workspace/myproject
python -m pip install -r requirements.txt
python train.py --help
```

추가 의존성이 없다면 불필요한 설치 단계를 만들지 않는다. 별도로 작은 입력으로 끝나는 실제 스모크 실행 명령과 예상 산출물을 제공한다.

### 서버 창: 본 실행과 상태 확인

```bash
lab-env run research "cd /workspace/myproject && python -u train.py --epochs 20 --output-dir runs/exp01"
lab-env jobs research
```

- 로그는 서버 `~/workspace/logs/`에서 확인한다. 로그 파일명은 실제 생성된 이름을 확인하도록 안내한다.
- 출력 파일의 위치와 형식, 결과를 PC로 가져오는 방법, 학습을 이어가는 실제 재개 명령을 적는다.
- 중단 방법은 본인이 실행한 작업을 대상으로 설명한다. 환경 전체를 중지하면 그 안의 다른 작업도 종료된다는 점을 표시한다.
- README의 각 명령에는 PC·서버·환경 중 어느 창에서 실행하는지 적는다. `lab-*`는 컨테이너 안에서 실행하지 않는다.
- 위 명령 흐름을 설명할 때 SSH는 명령을 전달하고 실제 계산은 서버에서 이루어짐을 분명히 한다.

## 8. 서버 운영 범위

- 일반 연구원에게 관리자 권한이 없다는 전제로 작성한다. 특정 계정에 예외적으로 권한이 있어도 코드 실행의 필수 조건으로 삼지 않는다.
- 호스트의 `/etc`, SSH, 방화벽, NVIDIA 드라이버, Docker 데몬, 사용자·그룹, systemd, 쿼터를 프로젝트 설치 스크립트에서 수정하지 않는다. 서버 재부팅·업그레이드를 자동 실행하지 않는다.
- 직접 Docker 설정이 필요한 특별한 경우에도 기존 Rootless Docker·CDI 방식을 따른다. 기존 도구를 우선 사용하고 `sudo docker`, 특권 컨테이너, Docker 소켓 마운트를 기본 전제로 넣지 않는다. 이 서버의 GPU 연결은 `--gpus` 대신 CDI 방식이다.
- 서버 안에서 작업한다면 `/usr/local/share/pilab/AI_GUIDE.md`가 있는지 확인하고 읽는다. 서버 밖에 있어 접근할 수 없다면 읽었다고 주장하지 않는다.
- 실제 GPU 작업 전에는 `lab-status`를 확인하고 운영 규칙을 따른다. 코드 작성 요청만으로 긴 학습이나 서버 운영 변경까지 요청받았다고 해석하지 않는다.
- 계정·비밀키·토큰을 코드와 로그에 넣지 않는다. 연구원끼리 계정이나 SSH 비밀키를 공유하는 실행 방식을 만들지 않는다.

## 9. API·웹 화면이 명시적으로 필요한 경우

일반 연구 스크립트를 전달하는 작업에 API 서버나 웹 화면을 기본으로 추가하지 않는다. 사용자가 서비스를 요청한 경우에만 적용한다.

- 기존 도구는 컨테이너의 `8000`번을 API 용도로, `8888`번을 Jupyter 용도로 매핑한다. 서버 측 공개 주소는 `127.0.0.1`이며 실제 호스트 포트는 `lab-env list`로 확인한다. 사용자·환경마다 달라지는 호스트 포트를 코드에 고정하지 않는다.
- 포트 매핑으로 접근할 앱은 컨테이너 안에서 `0.0.0.0:8000`으로 수신하고, 접속자는 SSH 포트 전달을 사용한다. 컨테이너 내부의 수신 주소와 서버 외부 공개 여부를 구분한다.
- 현재 네트워크는 승인된 연구실 PC의 SSH 접속을 전제로 한다. 서버 IP의 `8000`번으로 누구나 직접 접속할 수 있다고 안내하지 않는다.
- 장시간 GPU 요청의 동시 실행 수와 메모리 점유를 제한하고 종료 방법을 제공한다. GPU 메모리를 붙잡는 서버를 연구 작업 종료 후 계속 켜 두는 것을 기본값으로 삼지 않는다.
- 상시 서비스·자동 재시작이 필요하면 별도 요구사항으로 다루고, 관리자 운영 정책과 구현 범위를 먼저 확인한다.

## 10. 전달 완료 기준

프로젝트 규모와 작업 종류에 맞게 다음을 확인하고 결과를 보고한다.

- 필요한 파일·의존성·데이터 준비법·실행 명령이 함께 제공되는가?
- 개발 PC의 경로·계정·운영체제에 묶인 부분이 없는가?
- 기본 이미지와 추가 패키지가 호환되는가? 확인한 환경과 남은 불확실성은 무엇인가?
- CLI 또는 기존 실행 진입점이 정상 동작하고, 작은 입력 실행이 예상한 결과 파일을 만드는가?
- 장시간 학습이라면 체크포인트 저장·불러오기를 작은 실행으로 확인했는가?
- README의 명령이 실제 구현된 옵션과 일치하는가?

가능한 범위에서 변경에 맞는 검증을 수행하되, 코드 전달을 위해 긴 전체 학습을 반드시 돌릴 필요는 없다. 실제 서버·GPU·실데이터 검증을 하지 못했다면 그 범위를 명시하고, 사용자가 수행할 짧은 검증 명령을 제공한다. 문법 검사나 CPU 실행만으로 “서버 GPU 검증 완료”라고 쓰지 않는다.

최종 설명에는 변경 내용, 설치·실행·재개 명령, 출력 위치, 실제 수행한 검증과 미검증 범위를 포함한다.
